# GDD 미결 항목 (기획 결정 요청)

`docs/GDD.md` 기준으로, **아직 정해지지 않아 구현이 진행되지 않거나 가정으로 진행 중인 항목**만 모았다.
이미 확정된 규칙은 여기 없다. GDD 본문을 보면 된다.

우선순위는 **"안 정하면 무엇이 막히는가"** 기준이다.

| 구분 | 성격 | 지금 상태 |
|---|---|---|
| **A** | 구조 결정. 나중에 바꾸면 에셋·코드 재작업 | 구현이 곧 부딪힘 |
| **B** | 적 전투 구현 전 필요 | 플레이스홀더로 우회 중 |
| **C** | 수치만 채우면 됨. 구조 영향 없음 | 임시값으로 동작 |
| **D** | MVP 이후 / 범위 밖 | 논의 전 |

---

## A. 지금 결정이 필요한 것

### A-1. 버블 색의 원천이 두 곳이다

§2.3에서 `CharacterSO.mainColor`가 생기면서, "이 버블은 무슨 색인가"에 답하는 곳이
`CharacterSO.mainColor`와 `BubbleSO.bubbleColor` **둘**이 됐다.

**안 정하면 생기는 일** — 두 값이 어긋나면 같은 캐릭터의 스킬 3종이 서로 다른 색으로 보인다.
이 저장소는 이미 한 번 물렸다. `T_B_3`가 다른 두 개와 미세하게 다른 초록색을 들고 있었고
(`0.241, 1, 0` vs `0, 1, 0`), 최근 커밋에서 되돌렸다. 구조가 그대로면 다시 어긋난다.

| 선택지 | 내용 | 대가 |
|---|---|---|
| **(a) 추천** | `mainColor`가 단일 원천. `BubbleSO.bubbleColor` 제거 | 필드 1개 제거, 에셋 10개 재직렬화, 뷰의 색 지정 경로 변경 |
| (b) | `bubbleColor` 유지. `mainColor`는 카드 UI 전용으로 한정하고 "한 캐릭터의 3종은 같은 색" 규칙을 명문화 | 규칙을 사람이 지켜야 함. 검증 장치 없음 |

(a)를 권한다. §2.2의 "캐릭터 = 색, 스킬 = 문양"과 정확히 일치하고, **어긋날 수 없는 구조**가 된다.
뷰는 §2.3의 역참조 인덱스로 캐릭터를 찾아 그 색으로 칠하면 된다.

### A-2. 역참조 테이블의 소유자

§2.3은 `CharacterSO ↔ PlayerActor ↔ BubbleSO` 매핑을 `PuzzleManager`가 구축하도록 정했다.

**안 정하면 생기는 일** — `PuzzleManager`가 전투 액터를 알게 된다.
AGENT.md §1은 `PuzzleManager`를 "`PuzzleModel`과 `PuzzleView`를 잇는 유일한 지점"으로 정의한다.
퍼즐 담당이 전투를 알기 시작하면 이후 전투 변경이 퍼즐 코드를 계속 건드린다.

| 선택지 | 내용 |
|---|---|
| (a) | §2.3 그대로. `PuzzleManager`가 전부 소유 |
| **(b) 추천** | 정적 관계(`DeckSO` ↔ `BubbleSO`)는 `PuzzleManager`, 런타임 관계(`CharacterSO` ↔ `Actor`)는 `ActionManager` |

(b)를 권한다. §4.5의 실행 경로가 이미 `PuzzleManager` → 레시피 → `ActionManager`이므로,
`PuzzleManager`는 `BubbleSO` 스냅샷만 넘기고 `ActionManager`가 `caster`를 역추적하면
**`PuzzleManager`는 `Actor`를 몰라도 된다.**
§3.2.1의 재정규화와 회색조 판정은 `CharacterSO.skills` 배열만 있으면 되므로 `Actor`가 필요 없다.

문서 §2.3 세 번째 불릿의 문구만 고치면 된다.

## B. 적 전투 구현 전에 필요한 것

### B-1. 적 NPC 정의가 통째로 없다

필요한 것: **마릿수, `MaxHP`, `MaxShield`, 공격 주기(초), 스킬 구성, 패턴의 실체.**
§4.2에 "예: 3초"만 있다.

**안 정하면 생기는 일** — 전투 루프를 돌려볼 수 없다. 구조 검증조차 안 된다.

당장은 아래 플레이스홀더로 진행할 수 있다. 확정 수치가 오면 교체한다.

- 1마리 / `MaxHP` 3000 / `MaxShield` 0
- 3초마다 `AttackAction` + `HighestThreatEnemy` 단일 패턴

### B-2. 적 스킬을 담을 데이터 타입이 없다

지금 `BubbleSO`가 **"스킬 데이터"와 "버블 데이터"를 겸직**하고 있다.
적 스킬은 보드에 뜨지 않으므로 `bubbleImage`·`spawnWeight`·`mainColor`가 전부 무의미하다.

| 선택지 | 내용 |
|---|---|
| **(a) MVP 추천** | 당분간 `BubbleSO`를 재사용. 무의미한 필드는 비워둠 |
| (b) | `SkillSO`(수치·액션·타깃) / `BubbleSO`(스킬 참조 + 시각 + `spawnWeight`)로 분리 |

적 패턴이 2종 이상이 되는 시점에 (b)로 가는 게 자연스럽다. AGENT.md §10이 말한 "분리 축"이 하나 더 생긴 셈이다.

### B-3. `T_O` 효과가 미정

§3.3이 슬롯 구조(1개, 10% 지분)와 시전자 지정 규칙까지만 정했다. 효과 자체가 비어 있다.

정해야 할 것 셋.

1. **효과 내용** — 무엇을 하는가
2. **지속 범위** — 이번 `ChainStep`만인지, 이번 무브 전체인지, 전투 끝까지인지
3. **중첩 규칙** — 두 번 터졌을 때 곱인지 합인지, 상한이 있는지

증폭·버프류로 간다면 §4.5의 **선배치 실행 규칙**이 이미 대비돼 있다. 순서 문제는 걱정하지 않아도 된다.

## C. 수치만 채우면 되는 것

구조에 영향이 없다. 임시값으로 이미 동작하고, 밸런스 단계에서 채우면 된다.

### C-1. 캐릭터 3인의 기본 스탯
`MaxHP`, `MaxShield`, `BaseThreat` × 3명.
`BaseThreat`는 전투 시작 시 적의 첫 타깃과 `T_O` 시전자를 결정하므로(§3.3),
**3명이 서로 달라야** 의미가 생긴다.

### C-2. 스킬 9종의 실제 구성 — **여기가 제일 비어 있다**

현재 버블 에셋 9종이 **전부 같은 액션·같은 타깃**이다 (`AttackAction` + `LowestHPEnemy`).
`spawnWeight`는 전부 `1`, `value`는 전부 `10`, `chainWeights`는 비어 있다(배율 1.0).

즉 **지금은 캐릭터 3인의 성격이 완전히 동일하다.** 딜러/탱커/힐러 같은 역할 분화가 성립하려면
스킬별로 아래를 배정해야 한다.

| 항목 | 선택지 |
|---|---|
| `action` | `AttackAction` / `DefenseAction` / `HealAction` |
| `target` | `HighestThreatEnemy` / `LowestHPAlly` / `LowestHPEnemy` / `AllEnemies` / `AllAllies` / `AllActors` / `RandomActor` |
| `value` | 1버블당 기본 수치 |
| `spawnWeight` | 캐릭터 지분 30% 안에서의 상대 비중 |
| `chainWeights` | 연쇄 차수별 배율 (없으면 비워둠 = 1.0) |

### C-3. `Threat` 계산 계수
- 딜 1당 / 힐 1당 위협도 기여 비율
- 어그로 스킬의 강제 상승이 **절대값인지 배수인지**, **즉시인지 지속인지**
- 윈도우 실제 값 (§4.1에 "예: 최근 10초"만 있음)

## D. MVP 이후 / 아직 범위 밖

- **스테이지 구조** — 웨이브가 있는가, 리트라이 규칙
- **승패 후 처리** — 결과 화면인지 씬 전환인지. §4.4는 `GameEndState` 진입까지만 정의
- **가챠·수집 UI, 캐릭터 육성** — §1에서 1차 MVP 스코프 외로 명시됨
- **QoL 배속 노출 방식** — §4.7에서 허용은 됐으나 UI 위치·배율 단계 미정
