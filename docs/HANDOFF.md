# HANDOFF — 다음 세션 개발자를 위한 인수인계

3매치 퍼즐 코어와 **전투 실행 경로가 끝까지 이어졌다.** 스왑하면 실제로 적 HP가 깎인다.
비어 있는 것은 **적의 반격, 승패, 화면 표시**다. 즉 아직 "질 수 없는 게임"이다.
이 문서는 "무엇을 어떤 순서로, 무엇을 조심하며" 만들지를 넘긴다.

## 0. 읽는 순서

1. `CLAUDE.md` — 프로젝트 규칙 진입점
2. `docs/AGENT.md` — **반드시 읽는다.** 이 저장소에서 실제로 터진 버그에서 나온 규칙들이다
3. `docs/GDD.md` — 게임 기획서. 전투 규칙의 단일 원천
4. `docs/GDD-TODO.md` — 기획 결정 이력과 남은 논의 항목
5. 이 문서

`AGENT.md`를 건너뛰면 같은 버그를 다시 만든다. 특히 §3(영수증), §5(판정 단일화), §7(DOTween), §9(불변식).

## 1. 지금 어디까지 되어 있나

### 동작하는 것
3매치 퍼즐 코어 전체 — 보드 생성, 스왑/롤백, 연쇄, 중력·리필, 데드락 셔플, 힌트, 오브젝트 풀, 드래그 입력, DOTween 연출.

전투도 한 바퀴 돈다.

```
GameWaitState → (스왑) → GamePuzzleActionState → GameActionState → GameWaitState
                          연쇄 연출 완주            스킬 일괄 실행
```

- 덱 3인 + 적 1마리가 `Battlefield`에 서고, 버블 색이 `CharacterSO.mainColor`에서 나온다
- 퍼즐이 터진 덩어리를 영수증에 적고 → `ActionManager`가 스킬로 해석 → 수치 적용 → `BattleReceipt` 작성
- `ActionTarget` 7종 전부 동작. 위협도 적립도 돈다

### 비어 있는 것
| 대상 | 상태 |
|---|---|
| 적 NPC 공격 / `GameTime` | **없다.** `GameWaitState.OnUpdate()` 빈 몸통, `Battlefield.GameTime`이 0에 고정 |
| `GameEndState` | 클래스 없음. 부팅 시 `찾지 못했습니다` 경고가 뜬다 (정상) |
| `UIManager.cs` | **0바이트 빈 파일** |
| 전투 연출 | 없다. `BattleReceipt`를 소비하는 쪽이 아직 없어 로그만 찍는다 |
| `PuzzleFactory` | 후보는 덱에서 오지만 **균등 추첨.** 3:3:3:1 2단계 추첨 미구현 |
| `T_O` 증폭 | 회복(50×matchCount)만 구현. 1.2배 증폭 액션이 없다 (`IsPreemptive` 이음매만 있음) |
| 사망 처리 | 코드는 있으나 **한 번도 실행된 적 없다.** 적 HP 3000에 도달 못 함 |
| `PuzzleWaitState.OnAllTasksComplete` | `NotImplementedException`. 아무도 부르지 않아 무해 |

### 검증되지 않은 채 남은 것 — 전부 [7]에서 풀린다
적이 때리질 않으니 확인할 수가 없었다.

- **위협도** — 쌓이는 코드는 돌지만 값을 볼 수단이 없다. `HighestThreatEnemy`도 적이 1마리라 자명하게 통과했을 뿐
- **실드 흡수 분해** — 실드 75가 쌓여도 맞을 일이 없다
- **사망** — `[사망]` 표시, 사망 후 타깃 제외, 죽은 캐릭터 버블의 스킬 무효화
- **`chainWeight`** — 에셋이 전부 비어 있어 배율 1.0. 곱셈이 도는지 구별 불가

## 2. 역할 분담 — 기획자가 따로 있다

**`docs/GDD.md`와 `docs/GDD-TODO.md`는 기획자 소유다. 개발자가 임의로 고치지 않는다.**

기획에 손댈 일이 생기면 **제안하고 기다린다.** 승인이 확인되면 개발자가 직접 `GDD.md`를 고쳐도 된다.

**푸시는 개발자가 한다.** 단, 기획 문서 변경이 섞인 커밋은 **기획자 승인이 확인된 뒤에만** 올린다.
관문은 푸시라는 동작이 아니라 승인 여부다. 승인 없이 고친 문안이 원격에 올라가면
"결정한 적 없는 것이 결정된 것처럼" 남는다.

판단 기준은 "코드만 바뀌는가"가 아니라 **"GDD 문장이 틀리게 되는가"**다.
순수 리팩터링처럼 보여도 GDD가 주체나 시점을 명시해둔 부분을 옮기면 문안이 무효화된다.
착수 전에 GDD를 검색해 해당 문장이 있는지부터 본다.

경험상 아래 형식으로 보고하면 반영이 빨랐다.

1. **무엇이 막히는가** — 안 정하면 어떤 구현이 멈추는지 구체적으로
2. **선택지** — 2~3개, 각각의 대가와 함께
3. **추천 하나** — 근거와 함께. 나열만 하면 결정이 되돌아온다
4. **영향 범위** — 에셋 몇 개, 코드 어디

`docs/AGENT.md`(개발 컨벤션)도 마찬가지다. `CLAUDE.md`가 명시하듯 **임의 추가하지 말고 사용자에게 제안한다.**

## 3. 사용자(개발자) 작업 성향

- **한국어로 소통한다.** 지시는 짧다. 짧은 지시를 넓게 해석하지 말 것
- **초안 → 평가 → 수정 루프를 선호한다.** 결과물을 던지고 "평가"를 반복 요청한다. 비판은 구체적이고 근거 있게, 잘된 부분도 명시적으로
- **결정을 물으면 추천을 원한다.** 선택지만 나열하면 다시 물어본다. 추천 하나 + 근거 + 대가를 함께
- **스코프를 임의로 넓히지 않는다.** "선행작업 5개 진행"처럼 단위를 명시해 승인한다. 그 밖의 것은 발견해서 보고하되 손대지 않는다
- **규칙에는 "왜"를 요구한다.** `AGENT.md` §0대로, 규칙을 어길 땐 먼저 말하고 주석에 이유를 남긴다
- **검증 못 한 것은 못 했다고 말해야 한다.** 특히 컴파일 (아래 §6)
- 커밋 메시지는 **한국어, 제목 한 줄 + 빈 줄 + 본문에 왜.** 버그 수정은 증상이 아니라 원인을 적는다

## 4. 작업 목록과 선행 순서

**[0]~[5]는 완료됐다.** 남은 것은 아래와 같다.

```
            [7] 적 NPC + GameTime ── 여기서 미검증 4건이 한꺼번에 풀린다
                    │
                    ▼
            [8] GameEndState + 승패
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
   [6] 2단 추첨          [9] 연출 + UIManager
      + 사망 재정규화        BattleReceipt 소비
                              │
                              ▼
                     [10] T_O 증폭 + 사망 버블 회색조
```

| # | 작업 | 선행 | 비고 |
|---|---|---|---|
| 6 | `PuzzleFactory` 3:3:3:1 추첨 + 사망 재정규화 | 8 | `OnCharacterDied` 구독. 후보 목록은 이미 덱 기반 |
| 7 | 적 NPC 타이머 + `GameTime` | — | **다음에 할 것.** 프리즈 연동, `Battlefield.GameTime` 구동 |
| 8 | `GameEndState` + 승패 | 7 | **클래스명 주의** (§5). 적이 때려야 질 수 있다 |
| 9 | 전투 연출 + `UIManager` HP바 | 7 | `BattleReceipt` 재생. **소비자는 하나여야 한다** (§5) |
| 10 | `T_O` 증폭 액션 + 사망 버블 회색조 | 8,9 | `IsPreemptive` override 한 줄이면 켜진다 |

**[7]을 먼저 하는 이유**는 §1에 적은 미검증 4건(위협도·실드 흡수·사망·`chainWeight`)이 전부 "적이 때려야" 확인되기 때문이다.
[7]과 [8]은 붙여서 가는 편이 자연스럽다 — 적이 때리면 아군이 죽는데 `GameEndState`가 없으면 죽고도 게임이 계속된다.

### [9] 연출을 시작하기 전에 정할 것

연출의 **내용**(모션, 시간, 데미지 숫자 스타일, 캐릭터 스프라이트)은 아직 기획이 없다.
다만 **구조는 이미 정해져 있어** 지금 시작해도 막히지 않는다.

- 수치는 이미 다 끝나 있다. 연출은 `BattleReceipt`를 위에서 아래로 재생만 한다
- 스킬 1건당 연출 1건으로 순차 재생하는 것은 그 위에서 자유롭게 구성한다
- 연출 담당이 `ActionManager` 안에 살지 별도 매니저로 나갈지만 정하면 된다.
  **별도로 빼면** `MoveReceipt`와 같은 모양으로 `GameManager` 중계를 놓는다 (§5)

## 5. 반드시 지킬 것 (이 저장소에서 실제로 물린 것들)

### 논리는 미리 끝내고, 연출은 재생만 한다
퍼즐이 `MoveReceipt`를 쓰는 것과 **같은 구조를 전투에도 쓴다.**

```
퍼즐   Swap()     → MoveReceipt   → PuzzleMatrixView가 재생
전투   스킬 실행   → BattleReceipt → 연출 담당이 재생
```

"실행하고 바로 연출, 다음 스킬 실행하고 연출"로 번갈아 하고 싶어지는데, **화면은 어느 쪽이든 똑같다**
(스킬 1건당 연출 1건). 차이는 모델이 언제 바뀌느냐뿐이고, 번갈아 하면 이렇게 된다.

- **연출이 끊기면 데미지가 사라진다.** 프레임 스파이크로 트윈이 스킵되면 그 스킬은 실행 자체가 안 된다.
  `AGENT.md` §7이 적어둔 사고와 같은 원인인데, 결과가 "안 보임"이 아니라 "수치 증발"이라 재현도 안 된다
- **배속이 밸런스를 건드린다.** GDD §4.7이 배속을 허용한 근거가 "연출 속도가 수치에 영향을 주지 않는다"인데 그게 깨진다
- **정지 지점이 스킬 수만큼 는다** (`AGENT.md` §8)

### 레시피로 결과를 재계산할 수 없다
"어차피 레시피에 다 있으니 연출 시점에 다시 계산하면 되지 않나"가 틀리는 이유다.
**타겟팅이 의존하는 상태를 같은 배치의 스킬들이 바꾼다.**

- `LowestHPAlly`/`LowestHPEnemy` — 앞선 힐·딜이 체력 순위를 바꾼다
- `HighestThreatEnemy` — 스킬마다 위협도가 쌓인다
- `RandomActor` — **다시 뽑으면 다른 대상.** 재계산 자체가 불가능하다
- 실드가 30 흡수하고 HP가 70 깎인 **분해**, 오버킬 초과분을 뺀 **실제 적용량** — 재계산으로는 안 나온다

그래서 `BattleStep`이 요청량과 실제 적용량을 **둘 다** 들고, 적용 직후의 HP·실드까지 실어 보낸다.

### 스펙 스냅샷은 터뜨리는 순간에 잡아야 한다
`Bubble.ReturnToPool()`이 `_spec = null`을 하고, 그 호출이 **팝 트윈의 `OnComplete`에 걸려 있다.**
연출이 끝난 뒤엔 무슨 버블이었는지 되찾을 방법이 없다.
`MatchGroup.Spec`이 존재하는 유일한 이유이며, **퍼즐 모델이 반드시 해야 하는 일은 이것 하나뿐이다.**

### 층 — 퍼즐은 사실만, 전투는 해석
한 번 잘못 그었다가 되돌렸다. 처음엔 `PuzzleModel.Swap()`이 스킬 레시피를 작성하고
실행 장부(`Consumed`)까지 들고 있었는데, **버블을 터뜨리는 층이 전투 개념을 아는 구조**였다.

- 퍼즐 → `MatchGroup { Spec, Cells }`. "무슨 버블이 몇 차에 몇 개 터졌나"까지
- 전투 → `ActionManager`가 스킬로 해석. 덩어리 1개 = 스킬 1건, 차수·개수 계산, 선배치 정렬, 실행
- **매치 그룹 경계가 곧 스킬 경계다.** 평면으로 세면 보드 양쪽의 무관한 3매치가 6개짜리 하나로 뭉쳐 데미지가 두 배가 된다

`matchCount`와 `chainIndex`는 매치 그룹 구조에서 파생되는 값이라, 퍼즐이 따로 적으면 같은 사실의 기록이 두 벌이 된다.

### 실행 경로는 하나뿐이어야 한다
스킬은 멱등이 아니다. `BubbleSO.Execute()`를 지운 이유가 이것이다 —
`ActionManager`와 별개로 스킬을 실행할 수 있는 함수가 남아 있으면 그중 하나가 이중 적용이 된다.

같은 이유로 **전투 영수증의 소비자도 하나여야 한다.** 연출 담당과 UI가 각각 꺼내가면
"꺼내면 비워진다"가 깨져 한쪽이 빈손이 된다. GDD §4.1대로 **연출이 타임라인을 만들고 HP바는 거기 얹힌다.**

### 시전자를 못 찾는 두 경우를 구별하라
**실제로 이번에 넣었다가 잡은 버그다.**

- 소속 캐릭터가 **죽었다** → 스킬 무효. 다른 아군이 대신 쓰지 않는다 (GDD §3.2.1)
- 소속 캐릭터가 **없다**(공용 버블 `T_O`) → 생존 아군 중 `BaseThreat` 최고가 시전 (GDD §3.3)

둘을 뭉뚱그려 "생존 아군 중 최고"로 넘기면 **죽은 캐릭터의 버블이 남의 손을 빌려 계속 발동한다.**
아무도 안 죽는 동안에는 드러나지 않는다.

### 오버킬 시 연출을 끊지 마라
적 HP 0에서 즉시 전이하면 진행 중인 시퀀스가 남고, `ReturnToPool()`이 안 불린 뷰가 `dataViewDict`에 남는다.
`AGENT.md` §9의 불변식 `dataViewDict.Count == Size * Size`가 깨진다.
**수치는 즉시, 상태 전이는 `OnComplete` 이후.** (GDD §4.4)

### FSM 상태 클래스 이름
`AutoInsertStates()`가 `{Owner}{State}State`를 리플렉션으로 찾는다.
`GameManager` → `"Game"`, `EGameState.End` → **`GameEndState`**.
틀리면 컴파일은 되고 **경고 한 줄 뒤 조용히 동작하지 않는다.**

### 매니저를 새로 만들면 완수 보고를 잊지 마라
**이번에 걸릴 뻔했다.** `BaseManager`를 상속하는 순간 `EGameState.Init` 구독자 수가 늘어나는데,
`GameInitState`는 그 수만큼 완수 보고를 기다린다. `OnInit`에서 보고하지 않으면 `1/2`에서 멈추고
**보드는 뜨는데 입력이 안 먹는다.** (`AGENT.md` §8)

### 영수증은 불변, 그 사이 세계는 변한다
- **재정규화는 다음 스왑부터** — `Swap()`이 리필까지 다 뽑아둔 뒤라 이번 무브엔 반영 못 한다 (GDD §3.2.1)
- **사망 스킬 무효 판정은 실행 시점** — 작성 시점에 박아두면 연쇄 중간 사망을 놓친다

### 계층
- 뷰는 게임 규칙을 판단하지 않는다. 연출만 하고 스킬 발동에 관여하지 않는다
- `PuzzleManager`는 `Actor`를 직접 참조하지 않는다. 사망은 `ActionManager`가 `OnCharacterDied`로 재발행 (GDD §2.3, §3.2.1)
- **하위 매니저끼리 직접 소통하지 않는다.** `GameManager`를 거친다.
  단, **소비자가 하나뿐이면 중계를 놓지 않는다** — 전투 영수증이 `GameManager`를 안 거치는 이유다 (`AGENT.md` §10)

### 시계가 둘이다
`GameTime`(프리즈 제외 유효 전투 시간, 적 타이머·위협도 윈도우)과 `Time.time`(DOTween 연출)은 **다른 시계다.**
`Actor`는 시각을 **인자로 받는다**(`AddThreat(amount, gameTime)`). 시계는 `Battlefield`가 든다.
현재 `Battlefield.GameTime`은 **0에 고정**이라 위협도 누적이 만료되지 않는다. [7]에서 흘려보내야 한다.

## 6. 검증 제약 — 컴파일을 확인할 수 없다

이 저장소에는 Unity 참조 어셈블리가 없다. **에이전트는 컴파일 여부를 검증할 수 없다.**
코드를 고친 뒤에는 항상 "에디터에서 컴파일 확인이 필요하다"고 명시한다.

**현재 `main` 기준 코드는 에디터에서 검증된 상태다.** 매 변경마다 아래를 받아 진행했다.

- [ ] 컴파일 통과
- [ ] 부팅 로그 — `GameManager 4개` / `PuzzleManager 3개` / `전장 구성 완료. 아군 3인, 적 1마리`
      (`GameEndState를 찾지 못했습니다` 경고는 **정상**. 작업 [8]이다)
- [ ] 스왑 → 연쇄 → 셔플 무회귀
- [ ] `[ActionManager] 전투 N건` 로그에 수치가 기대값과 맞는지

> `.meta`를 **손으로 쓰지 않는다.** 스크립트만 만들고 에디터가 guid를 발급하게 한다.
> 파일을 옮길 땐 `git mv`로 `.cs`와 `.meta`를 **함께** 옮긴다. 따로 옮기면 guid가 갈려 `.asset` 참조가 끊긴다.
> 문제가 생겨도 `.meta`를 지우고 재생성하면 안 된다. `.asset`까지 함께 지우고 메뉴에서 새로 만드는 편이 안전하다.

### 임시 로그가 유일한 검증 수단이다

전투 결과를 볼 화면이 아직 없다. `ActionManager.ReportBattleReceipt`가 그 자리를 대신한다.

```
[ActionManager] 전투 2건
  A -T_A_1-> Enemy Damage 60(요청 60) HP 2880/3000 실드 0
  B -T_B_3-> Enemy Damage 30(요청 30) HP 2850/3000 실드 0
```

**[9] 연출이 이 영수증을 소비하기 시작하면 제거한다.** (`AGENT.md` §9 — 조사용 로그는 원인을 잡은 뒤 제거)

## 7. 이미 세운 가정 / 아직 미결

**확정된 것** (이 세션에서 결정)

- **캐릭터 실드 초기값은 0.** 흡수막은 `DefenseAction`으로 부여받고 `maxShield`는 상한이다
- **`T_O` 색은 노랑**(목업). 소속 캐릭터가 없어 `mainColor`를 물려받지 못해 `PuzzleManager`가 폴백으로 답한다
- **스킬 실행은 전용 상태(`GameActionState`)에서 일괄** — 기획자 승인. GDD §4.4/§4.5 반영 완료
- **`BattleReceipt` 신설** — 기획자 승인. GDD §4.5 반영 완료
- **스킬 레시피 작성 주체는 `ActionManager`** — GDD §4.5 반영 완료

**가정하고 진행 중** (기획자 확정 전, 코드 주석에 근거를 남길 것)

- **실드·힐의 상한 초과분도 위협도에 포함**한다 (실제 적용량이 아니라 부여량 기준). 탱커가 방어 행위를 계속하는 한 어그로를 유지하는 게 의도에 맞다고 판단
- **`T_O` 증폭 리셋 트리거**는 GDD가 `PuzzleWaitState` 복귀로 적었지만, 증폭은 전투 수치라 소유자가 `ActionManager`다. **`GameActionState` 퇴장 시점**으로 구현할 계획

**미결 (GDD §D)** — 스테이지·웨이브·리트라이, 승패 후 결과 화면/씬 전환, 가챠·육성(MVP 외), 배속 UI

**미결 (연출)** — 모션·시간·데미지 숫자 스타일·캐릭터 스프라이트. **구조는 정해져 있어 [9] 착수를 막지 않는다** (§4)

### 목업이라는 것을 잊지 말 것

**캐릭터 3인과 그 스탯·스킬 값은 전부 목업이다.**
진짜 데이터는 메인 시스템 완성 후 **파싱 시스템이 외부 데이터에서 생성**한다.

GDD §2.4의 카탈로그도 마찬가지다. GDD-TODO가 "결정 완료"로 닫아둬서 확정값으로 오해하기 쉬운데 중간 산출물이다.
지금 값을 채운 목적은 **검증용 시드**뿐이다 — `BaseThreat`가 3인 모두 같으면 위협도 정렬이 도는지 구별할 수 없다.

> 파싱 시스템은 에셋을 **재생성하지 말고 기존 에셋을 찾아 필드만 덮어써야 한다.**
> 재생성하면 `.meta` guid가 갈려 `DeckSO.characters`와 인스펙터 배선의 참조가 전부 끊긴다.

**그 밖의 플레이스홀더** — `chainWeights` 전부 비어 있음(배율 1.0), 적 스킬은 `BubbleSO` 컨테이너 재사용,
`T_O`는 회복만 구현(증폭 없음), 스포닝은 균등 추첨(3:3:3:1 미구현)

## 8. 새 규칙을 만들게 되거든

구현하다 보면 컨벤션으로 굳힐 만한 판단이 나온다. **`AGENT.md`에 임의로 추가하지 말고 제안한다.**

**GDD도 마찬가지인데, 판단 기준이 "코드만 바뀌는가"가 아니라 "GDD 문장이 틀리게 되는가"다.**
스킬 레시피 작성 주체를 옮긴 건 순수 리팩터링처럼 보였지만 GDD §4.5 문안을 무효화했고,
사전 승인 없이 진행해 지적받았다. 착수 전에 GDD를 검색해 해당 문장이 있는지부터 본다.

아래는 전투가 붙으면서 새로 생긴 불변식 후보다 (`AGENT.md` §9 확장 제안 대상).

- 살아있는 `Actor`의 `CurrentHP > 0`, 죽은 `Actor`는 어떤 타깃 목록에도 없다
- 총 위협도 `>= BaseThreat` (실시간 누적은 음수가 되지 않는다)
- 한 `MoveReceipt`는 정확히 한 번만 소비된다 (`GameManager`가 보관, 꺼내면 비워짐)
- 완수 보고는 기다리는 수만큼만 온다 (초과 = 이중 보고. 각 상태가 검사 중)
- 연출 종료 시 화면 HP바 값 `==` 모델 `CurrentHP`

### 이미 코드에 들어간 위반 검사

로그는 **정상 흐름을 찍지 않고 깨진 것만 찍는다.** 이번에 FSM 전이 로그를 전부 걷어내고 아래로 교체했다.

- `AutoInsertStates` 상태 클래스 못 찾음
- 등록되지 않은 상태로 전이 시도 (이전 상태가 `OnExit`을 마친 뒤라 어디에도 속하지 않은 채 멈춘다)
- 완수 보고를 받지 않는 상태에 보고가 들어옴 (그 보고는 버려지고 누군가는 기다리다 멈춘다)
- 완수 보고 초과
- 소비되지 않은 영수증이 남은 채 `GameActionState` 퇴장
- 같은 버블이 두 캐릭터에 배정됨 (`PuzzleManager`·`ActionManager` 양쪽)
- 덱/공용 버블 미배정
