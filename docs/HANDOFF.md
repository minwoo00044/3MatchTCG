## 2. 역할 분담 — 기획자가 따로 있다

**`docs/GDD.md`와 `docs/GDD-TODO.md`는 기획자 소유다. 개발자가 임의로 고치지 않는다.**

기획에 손댈 일이 생기면 **제안하고 기다린다.** 이 저장소의 원격 푸시도 기획자가 한다.

경험상 아래 형식으로 보고하면 반영이 빨랐다.

1. **무엇이 막히는가** — 안 정하면 어떤 구현이 멈추는지 구체적으로
2. **선택지** — 2~3개, 각각의 대가와 함께
3. **추천 하나** — 근거와 함께. 나열만 하면 결정이 되돌아온다
4. **영향 범위** — 에셋 몇 개, 코드 어디

`docs/AGENT.md`(개발 컨벤션)도 마찬가지다. `CLAUDE.md`가 명시하듯 **임의 추가하지 말고 사용자에게 제안한다.**

## 3. 사용자(개발자) 작업 성향

- **한국어로 소통한다.** 지시는 짧다. 짧은 지시를 넓게 해석하지 말 것
- **초안 → 평가 → 수정 루프를 선호한다.** 결과물을 던지고 "평가"를 반복 요청한다. 비판은 구체적이고 근거 있게, 잘된 부분도 명시적으로
- **결정을 물으면 추천을 원한다.** 선택지만 나열하면 다시 물어본다. 추천 하나 + 근거 + 대가를 함께
- **스코프를 임의로 넓히지 않는다.** "선행작업 5개 진행"처럼 단위를 명시해 승인한다. 그 밖의 것은 발견해서 보고하되 손대지 않는다
- **규칙에는 "왜"를 요구한다.** `AGENT.md` §0대로, 규칙을 어길 땐 먼저 말하고 주석에 이유를 남긴다
- **검증 못 한 것은 못 했다고 말해야 한다.** 특히 컴파일 (아래 §6)
- 커밋 메시지는 **한국어, 제목 한 줄 + 빈 줄 + 본문에 왜.** 버그 수정은 증상이 아니라 원인을 적는다

## 5. 반드시 지킬 것 (이 저장소에서 실제로 물린 것들)

### 스킬 레시피는 `Swap()` 시점 스냅샷이어야 한다
`Bubble.ReturnToPool()`이 `_spec = null`을 하고, 그 호출이 **팝 트윈의 `OnComplete`에 걸려 있다**
([PuzzleMatrixView.cs:219](../Assets/_/_Scripts/InGame/Puzzle/PuzzleMatrixView.cs:219)).
즉 **콜백이 불리는 시점엔 `Spec`이 이미 null이다.** 연출 중에 조회하면 100% 실패한다.
`AGENT.md` §3 영수증 규칙의 네 번째 사례가 될 자리다.

### 스킬 실행은 멱등이 아니다
위치는 `ReconcileViewsToModel()`로 재보정해도 안전하지만 **데미지는 아니다.**
"콜백이 안 불렸을까 봐" 보조 경로를 두면 즉시 이중 적용이 된다. 레시피에 `executed` 플래그를 둬라.

### 오버킬 시 연출을 끊지 마라
적 HP 0에서 즉시 전이하면 진행 중인 시퀀스가 남고, `ReturnToPool()`이 안 불린 뷰가 `dataViewDict`에 남는다.
`AGENT.md` §9의 불변식 `dataViewDict.Count == Size * Size`가 깨진다.
**수치는 즉시, 상태 전이는 `OnComplete` 이후.** (GDD §4.4)

### FSM 상태 클래스 이름
`AutoInsertStates()`가 `{Owner}{State}State`를 리플렉션으로 찾는다.
`GameManager` → `"Game"`, `EGameState.End` → **`GameEndState`**.
틀리면 컴파일은 되고 **경고 한 줄 뒤 조용히 동작하지 않는다.**

### 매치 그룹 = 스킬 레시피 1건
`ChainStep.MatchGroups`는 평면 목록이 아니다. 평면으로 세면 보드 양쪽의 무관한 3매치가
6개짜리 하나로 뭉쳐 **데미지가 두 배가 된다.**

### 영수증은 불변, 그 사이 세계는 변한다
- **재정규화는 다음 스왑부터** — `Swap()`이 리필까지 다 뽑아둔 뒤라 이번 무브엔 반영 못 한다 (GDD §3.2.1)
- **사망 스킬 무효 판정은 실행 시점** — 작성 시점에 박아두면 연쇄 중간 사망을 놓친다

### 계층
- 뷰는 게임 규칙을 판단하지 않는다. 콜백으로 **`ChainStep` 인덱스만** 넘긴다
- `PuzzleManager`는 `Actor`를 직접 참조하지 않는다. 사망은 `ActionManager`가 `OnCharacterDied`로 재발행 (GDD §2.3, §3.2.1)

### 시계가 둘이다
`GameTime`(프리즈 제외 유효 전투 시간, 적 타이머·위협도 윈도우)과 `Time.time`(DOTween 연출)은 **다른 시계다.**

## 6. 검증 제약 — 컴파일을 확인할 수 없다

이 저장소에는 Unity 참조 어셈블리가 없다. **에이전트는 컴파일 여부를 검증할 수 없다.**
코드를 고친 뒤에는 항상 "에디터에서 컴파일 확인이 필요하다"고 명시한다.

**`deeafbd`가 아직 에디터에서 검증되지 않았다.** 다음 세션의 첫 작업은 이것이다.
확인할 항목:

- [ ] 컴파일 통과
- [ ] `ActionTarget` 에셋 7종이 인스펙터에서 정상 인식 (**손으로 작성한 `.meta` 4개 포함** — `AllActors`, `HighestThreatEnemy`)
- [ ] `BubbleSO` 10종의 `target` 참조가 안 끊겼는지
- [ ] 플레이 시 보드 생성 → 스왑 → 연쇄 → 셔플이 이전과 동일하게 동작 (매치 그룹 전환의 회귀 확인)
- [ ] 부팅 로그에 FSM 등록 경고가 없는지

> `.meta`가 문제를 일으켜도 **지우고 재생성하면 안 된다.** guid가 바뀌면서 `.asset`의 스크립트 참조가 끊긴다.
> `.asset`까지 함께 지우고 메뉴에서 새로 만드는 편이 안전하다.

## 7. 이미 세운 가정 / 아직 미결

**가정하고 진행 중** (기획자 확정 전, 코드 주석에 근거를 남길 것)

- **실드·힐의 상한 초과분도 위협도에 포함**한다 (실제 적용량이 아니라 부여량 기준). 탱커가 방어 행위를 계속하는 한 어그로를 유지하는 게 의도에 맞다고 판단
- **`T_O` 증폭 리셋 트리거**는 GDD가 `PuzzleWaitState` 복귀로 적었지만, 증폭은 전투 수치라 소유자가 `ActionManager`다. **연출 시퀀스 완주 시점**으로 구현할 계획

**미결 (GDD §D)** — 스테이지·웨이브·리트라이, 승패 후 결과 화면/씬 전환, 가챠·육성(MVP 외), 배속 UI

**플레이스홀더 상태** — `chainWeights` 전부 비어 있음(배율 1.0), 적 스킬은 `BubbleSO` 컨테이너 재사용

## 8. 새 규칙을 만들게 되거든

구현하다 보면 컨벤션으로 굳힐 만한 판단이 나온다. **`AGENT.md`에 임의로 추가하지 말고 제안한다.**
특히 아래는 전투가 붙으면서 새로 생길 불변식 후보다 (`AGENT.md` §9 확장 제안 대상).

- 살아있는 `Actor`의 `CurrentHP > 0`, 죽은 `Actor`는 어떤 타깃 목록에도 없다
- 총 위협도 `>= BaseThreat` (실시간 누적은 음수가 되지 않는다)
- 한 `MoveReceipt`의 스킬 레시피는 정확히 한 번씩만 실행된다
- 연출 종료 시 화면 HP바 값 `==` 모델 `CurrentHP`
